# 写作核心

本文件是 Lathe **写作型操作**（生成、续写、复习、收尾、面试文档）共用的单一事实源（教程结构、配额矩阵、标注、不变量、研究纪律、预检、自检）。仅这些操作需要读取；提问、标签、列表、扫描、验证等操作不加载本文件。

`<SKILL_DIR>` 指 SKILL.md 所在目录；`<TUTORIALS_DIR>` 指默认基础目录（`tutorials_base_path`）。

## 教程结构（单一事实源）

每篇教程（或系列的每个部分）遵循此结构，但章节*标题*必须特定于领域：

```
# [标题]

[引子——按需，建议 1-4 段；以建立问题和动机为准，不设段数上限]

## 你将构建什么
一段或几段。用控制性示例命名的具体最终状态。

## 前置条件
列表：需要安装的工具、读者应大致了解的知识。

## [可选：0-2 个地基章节——心智模型/术语/环境]   ← new 1-2 / adjacent 0-1 / beginner 可用；不计入 4-7
为什么需要先建立这个地基。一个可观察或可运行的小例子。不引入后文不会用到的概念。

## [可选：0-1 个承接章节——上一部分练习留下的问题]   ← 不计入 4-7，但计入总章 ≤9
把上一部分练习里引入、与本部分知识点没有交集的概念集中讲掉（≤2 条）。
放在这里而不是检查点之后：读者应该在开始动手前就知道欠账在哪。
每条都要讲透（定义 + 如何解释当时的疑问 + 1 个可运行验证），常见 150-400 字，**不设字数上限**——篇幅不占知识点配额；讲过的概念照样进 `covered_concepts`。

## [具体的章节标题——命名本章节创造的东西]
为什么需要它。小块代码，每块标注插入位置。旁白或设计笔记。
（本部分共 4-7 个此类构建章节，每章 1 个主知识点；紧耦合可 1 章 2 个，但主知识点总数 ≤7；地基 + 承接 + 构建 ≤9）

## 检查点
> [!PREDICT]   ← 每个检查点 1 个
> 运行之前：你预期会看到什么输出？
**运行以下命令验证：** + 预期输出 + 可能的错误

**本部分结束时的文件状态：** 用列表或一两句话列出新增/修改的文件、关键符号、可运行命令或产物；不新增 `##` 小节。

**下一部分起始状态：** 在 `## 接下来` 中至少写明：文件、函数/符号、可运行命令、尚未完成项。

**本部分不覆盖：** 用一句话说明本部分明确不解决什么，避免读者误以为已经完整。**若有顺延的知识点，在这里按积压 ID 点名并写「预计 Part N」**（如「3c Guard 的位置（积压 3c，预计 Part 4）」；不要只写「还有一些内容留给后面」）。

**练习承接：** 按三档写本部分练习引入的新概念的去向（无则写「无」），并**同时交代上一部分留给本部分的承诺是否兑现**——两件事不能混成一句「已并入」：
- 档 1 融入：`<知识点>` → 并入本部分 §X（三件套齐：疑问复述 + 解释 + 可运行验证），账本 `promised_by: part-<本部分>.md`、`depth: tier1`
- 档 2 承接章：`<知识点>` → 并入本部分 §0（同一行同时给积压/账本 ID）
- 档 3 顺延：`<知识点>` → 记入 `knowledge_backlog`，写「预计 Part N」+ 积压 ID，题面另加一行斜体提醒
- 上一部分的承诺：`<K>` → 本部分已讲透（§X）／**本部分没讲成，已顺延 Part N**（见 knowledge-ledger.md「承诺的兑现与回滚」）

## 接下来
寄语或前向钩子：最后部分邀请读者走出铺设的道路；非最后部分按需要命名 1 个或多个未决问题，倾向悬念感。随后用平实散文（不是标注）提出**结尾反思**：挑本部分最重要的一个设计决策，要求读者解释*为什么*而非*是什么*，不替他们回答。

## 练习（必做编号 3-5 个 + 选做 0-3 个，总 ≤8；每个具体到 30 秒内可开始）
**必做题最多 2 道引入本部分没讲过的新概念**，其余必做题只用已讲内容（巩固型）；引入新概念的必做题按knowledge-ledger.md「练习承接三档」落档，并进账本（`src: exercise`）。
档 3 的题，题面后用一行斜体告知读者：*本题涉及的知识点（X，积压 ID `K`）不在本部分展开，预计 Part N 讲。*（「预计」是因为还债节奏由名额表动态决定；实际讲到它的那一部分要在该章开头回指一句「这就是 Part M 练习 k 留下的 X」。）
**选做题可以引入新概念、不限数量，但每道必须附「线索 + 官方文档入口」**（一两句思路提示 + 一个深链接）；这些概念**默认不入积压、不进账本**，只当延伸阅读。用户之后想系统学其中某个，按普通清单条目提出即可。

## 来源（编号，格式：[标题](url) —— 一句话说明；数量不设上限，超过 5 条按主题分组）
```

每个部分以 *"在本部分结束时，你将拥有 [具体的东西]"* 开头，以检查点结尾。每个部分独立成篇。

**写作时按下方「配额矩阵」控制知识点范围，不要等写完再删。** 本文件的核心原则是：

> **配额只约束“讲几个知识点”，不约束“每个知识点讲多少”。**
>
> 配额回答本部分有几个构建章节、几个地基章节、几个练习、覆盖哪些术语；不回答每个知识点写几段、几句、用几个类比、几个标注、几行代码。
>
> 讲解深度以“六项讲透”为准：定义、动机、用法、例子、边界、验证。六项需要多少篇幅就写多少篇幅；需要类比就从读者熟悉的概念展开，需要完整代码就写完整代码。
>
> 如果本部分讲不清，优先减少知识点数量或拆分部分，而不是压缩每个知识点的解释。

**“超出”只按结构性范围判断，不按字数判断：**

- **知识点数量超出**：超过 7 个主知识点；或地基 + 构建超过 9 章；或单章包含超过 2 个彼此独立的知识点。
- **独立学习里程碑超出**：一个最终检查点已经无法覆盖本部分的完成标准，需要多个彼此独立的检查点/里程碑。
- **独立改动面/验证面超出**：代码跨多个独立编译/运行阶段，需要多张改动面表或多个集成检查点才能说清。
- **单次交付能力超出**：模型无法在一次输出中完整交付，或本部分明显包含多个独立学习 session。
以上**四项**中的任一项成立时，按知识点边界拆分部分；拆分后每部分仍要保持六项讲透、代码完整、检查点可执行。确需减少本部分讲的知识点数量时，把减掉的条目写进 `knowledge_backlog`（不要写进 `next_hook`——它下次续写会被覆盖；`course_plan` 只放 Part 级路线），不删内容。

**篇幅与行数不是上限。** 知识点讲透了，写多长都可以接受——篇幅是学习的成本，不是缺陷：它不增加知识点，也不制造冗余。判断"要不要拆"看上面四项（尤其是"读者能不能在一次学习 session 里独立走完"），**不看字数**。参考观察值：单部分正文（不含代码块与来源）约 10,000 个中文字符、单个 `runnable` 代码块约 100-120 行。**它们是提示，不是阈值**：到了观察值先问"里程碑该不该拆"，答案是不该，就照写不误。

**禁止的反动作**：为了控制篇幅压缩解释、删减知识点、砍掉类比/标注/验证，或为了低于观察值删掉运行必需代码。单个 `runnable` 的 100-120 行只是"可按文件/逻辑段拆成多个完整块"的信号，不是行数上限；大代码块的正确处理是**分段呈现**，不是裁内容。索引超出只归档，不压缩正文；研究预算单独计算，不影响正文长度。**解释长度、段落数、句子数、类比长度、标注数量不构成内容上限，不得因此删减内容。**

**一个知识点 = 读者在本节结束后应能用自己的话解释、并在教程的代码/命令/推导中复现的一个概念或技能。** 每个构建章节有 1 个主知识点；紧耦合的可以 1 章 2 个，但本部分总数 ≤7。若实际需要更多，拆成两个部分，或把剩余知识点按knowledge-ledger.md「知识点来源」写进 `knowledge_backlog`（不要写进 `next_hook`——它下次续写会被覆盖；`course_plan` 只放 Part 级路线，也不放条目），不要压进同一部分。

**按操作的结构变体（登记在此，不在别处另行定义）：**

| 操作 | 结构差异 |
|------|----------|
| 生成 part-01 | 如上，无 `[!RECALL]` |
| 续写 part-NN（N≥2） | 顶部加 `> [!RECALL]` 节拍；`## 接下来` **之前**插入 `## 目标达成回顾`；上一部分有档 2 时，在 `## 前置条件` 之后加承接章节（≤1 章、≤2 条） |
| 收尾 part-NN（总结部分） | 必备七节：`全课程回顾` / `知识图谱` / `目标对照` / `未讲清单（按 ID）` / `回顾自检`（代替 `## 检查点`）/ `练习方向` / `寄语`。**不写** `## 检查点`、`## 你将构建什么`、`## 前置条件`、`## 来源`、四个契约行（没有下一部分可交接）与验证状态横幅（它永不参与验证）。逐节内容与门禁联动见 extend.md「收尾模式」；`part_lint.py --kind finish` 按这张表检查 |
| 复习 part-NN-review | 完全独立的回顾结构，不遵循上表（详见 review.md） |
| 面试文档（复习/生成/续写产出的附加文件） | **完全独立的问答结构，不遵循本表**；**只对教学部分产出**（定义见 `interview.md`，此处不复述）。本文件对其**仅**提供「配额矩阵中的检索预算」与「有据可依或标记」不变量，**不提供**结构、标注规则与交付前自检 |

## 配额矩阵（单一事实源）

所有**知识点数量**、表达预算和流程预算集中在这里。其他模块只引用本表，不再重复数字。

**主题新颖度 `topic_novelty`**（写入 `metadata.json`）：

| 取值 | 含义 | 生成时默认推断 |
|------|------|----------------|
| `new` | 读者/模型对该主题几乎没有可靠先验，需要先建立地基 | `experience_level = beginner` |
| `adjacent` | 有相邻领域经验，核心概念可类比，具体 API/版本仍需查证 | `experience_level = familiar` |
| `familiar` | 已有同主题教程或 `sources` 覆盖，主要是复用与增量 | `experience_level = experienced` |

> 用户可在生成时覆盖默认推断。续写读取 metadata；字段缺失时按 `sources` / `covered_concepts` 的覆盖度推断，默认 `adjacent`。
>
> **误判保护：** 无法判断时按更高新颖度处理（`new` > `adjacent` > `familiar`）。如果用户说不出该主题的一个核心概念，按 `new` 处理，不要按 `familiar` 省研究预算。

### 1. 知识点配额（真正的范围控制）

| 项目 | 规则 | 说明 |
|------|------|------|
| 正文构建章节 | 4-7 | 每章 1 个主知识点；紧耦合可 1 章 2 个，但本部分主知识点总数 ≤7 |
| 地基章节（豁免） | new 1-2 / adjacent 0-1 / beginner 0-1 / familiar 0 | 不计入 4-7；**地基 + 构建 + 承接 ≤9** |
| 承接章节（豁免） | 0-1（≤2 条） | 上一部分练习引入、与本部分知识点无交集的概念；不计入 4-7，但计入总章 ≤9；讲过的照样进 `covered_concepts` |
| 用户显式清单 | 以清单为准 | 归一化后 ≤ 可用容量则全讲；超出按原顺序分批，剩余写入 `knowledge_backlog`（见knowledge-ledger.md「知识点来源」） |
| 必做练习 | 3-5 | 每个具体到 30 秒内可开始；**最多 2 道引入新概念**（按三档落档、进账本），其余为巩固型 |
| 选做练习 | 0-3 | 默认 0；总计 ≤8；可引入新概念、不限量，但每道附「线索 + 官方文档入口」，不入积压 |
| 术语定义 | 全部新术语 | 不设数量上限 |
| 课程路线图 | 3-12 项 | metadata 字段；不是 `index.md` |

**知识点配额是范围，不是目标。** 没有用户清单、也没有积压时，默认取“下限到中位数”（4-5 个）；**有用户清单或 `knowledge_backlog` 非空时，可用构建名额按 7 计**（见「名额分配」）——两种口径不混用。标“选做”的层默认 0。超过 7 个主知识点或 9 个总章节时，**先把超出的条目按原顺序写进 `knowledge_backlog` 并留延后提醒**，仍装不下再拆部分；两种情况都不压缩解释。

> **三者相加超过 9 时的让位顺序（0.6.0）：先减构建条数（按knowledge-ledger.md「知识点来源」入队），不减地基章节与 §0 承接章节**——后两者是本部分的前置欠账，删掉等于把旧账又推回去；承接仍 ≤1 章、≤2 条。

### 2. 表达与索引预算（按需，不作为讲透门禁）

| 项目 | 规则 | 说明 |
|------|------|------|
| 引子 | 建议 1-4 段 | 不设上限；以建立问题和动机为准 |
| 你将构建什么 | 一段或几段 | 讲清最终状态即可 |
| 接下来 | 按需 | 命名 1 个或多个未决问题 |
| 术语定义 | 结论先行，按需展开 | 不设句数上限 |
| 类比锚定 | 每个难概念 0-1 个 | 不设总数上下限；不硬造；讲清映射和失效边界 |
| 信息型标注（HEADS-UP/NOTE/TIP） | 按需 | 不设总数上限；每个对应具体知识点/真实陷阱 |
| ASIDE | ≤2/部分 | 装饰性旁白，保持简短；不承担教学功能 |
| DESIGN-NOTE | 每个独立设计决策 1 个 | 放章节末尾；不设每章 1 个的硬上限 |
| PREDICT | 每个检查点 1 个 | 每部分 1-3 个 |
| RECALL | part-01 为 0；part-02 起至少 1 个 | 按主要知识点边界增加，不以字数为触发 |
| 图表 | 按机制需要 | 一张图一个机制；节点 ≤12 |
| 代码块 | 由完整性决定 | 不设行数上限（单个 `runnable` 超过约 100-120 行时优先按文件/逻辑段拆块，不裁内容）；六类标记齐全：`runnable` / `fragment` / `exercise` / `text` / `output` / `expected_failure`，**未标记按 `runnable` 处理**（图表语言 `mermaid` / `plantuml` / `dot` 例外，未标记也视同 `text`） |
| 总结部分 | 不适用「构建 4-7 / 实写 N 章」 | 它不引入新知识点；回执那一行改写「总结七节 ✅」（`part_lint.py --kind finish` 输出） |
| 索引（continuity） | 2200 字软 / 3000 硬（须先守住各字段条数上限：`covered_concepts` 24 条、`open_threads` 8 条、`fixed_numbers` 18 项、`part_titles` 8 个部分） | 索引预算；超出只归档索引字段，不压缩正文；用 `ledger_check.py --continuity` 实测 |

### 3. 流程预算（与正文长度无关）

| 项目 | familiar | adjacent | new | 规则 |
|------|----------|----------|-----|------|
| 搜索调用（1 次可含 1-4 query） | 3 | 5 | 8 | 计调用，不计 query |
| 定向全文抓取 | 1-2 | 3 | 5-6 | 每次抓取一个命名问题 |
| 来源条数 | 不设上限 | 同左 | 同左 | `## 来源` 超过 5 条按主题分组 |

**使用规则：**

0. **本表是权威。** 本文件其他处的数字（结构模板、标注表、自检）是它的投影；调参时以本表为准，并同步检查投影是否一致。
1. **知识点配额**是范围，不是目标；无清单无积压时默认取下限到中位数，有清单或积压时构建名额按 7 计；标“选做”的层默认 0。
2. **表达与代码不设内容上限。** 讲清一个知识点需要多少段、多少句、多少个类比、多少行代码，就写多少；不因“配额的默认值”压缩解释。
3. **索引是预算，不是正文预算。** `continuity` 超出时归档或压缩索引字段，不删课程正文。
4. **“超出”只按结构性范围判断**（知识点数量、独立里程碑、独立改动面、单次交付能力）；触到时拆部分/减知识点，不删解释。

本部分讲哪些知识点、没讲的去了哪、怎么向用户交代——**来源优先级、清单归一化、名额分配、去重、积压闸门、写前计划确认、播报与覆盖回执、练习承接三档、延后提醒，以及知识点账本 `syllabus.json` 的结构与不变量**——全部在 `<SKILL_DIR>/references/knowledge-ledger.md`（单一事实源）。生成、续写、收尾必须读它；本文件只在需要处引用，不复述。

## 标注类型

| 标注 | 用途 | 频率 |
|------|------|------|
| `> [!PREDICT]` | 检查点前的预测提示 | 每个检查点 1 次；每部分 1-3 次 |
| `> [!RECALL]` | 第 N≥2 部分顶部的间隔检索 | part-01 为 0；part-02 起顶部 1 次；按主要知识点边界可增加，不以字数为触发 |
| `> [!HEADS-UP]` | 即将踩坑的警告 | 每个真实陷阱 1 次；**不设总数上限** |
| `> [!ASIDE]` | 词源、故事等旁白 | 装饰性；**≤2 次/部分**；保持简短，不承担教学功能 |
| `> [!DESIGN-NOTE]` | 多段落的"为什么"讨论 | 每个独立设计决策 1 次；放章节末尾；不设每章 1 个的硬上限 |
| `> [!UNVERIFIED]` | 无法确认的关键声明 | 按需；≥3 个关键事实时先补研究 |
| `> [!NOTE]` | 中性补充信息 | 按需；**不设总数上限**；每个对应具体知识点/真实陷阱 |
| `> [!TIP]` | 便捷技巧 | 按需；**不设总数上限**；每个对应具体知识点/真实陷阱 |

**使用规则（写完后必须自检，见文末"交付前自检"）：**

- **信息型标注**（HEADS-UP、NOTE、TIP）：不设总数上限，也不设每章节硬上限；每个标注必须对应一个具体知识点或真实陷阱。长解释优先写进正文散文，不要为了标注而标注。**不要为了满足数字删除教学警告或必要补充。**
- **旁白型标注**（ASIDE）：每部分 ≤2 个。旁白不是教学脚手架；若信息必须保留，改用 NOTE 或写进正文。
- **PREDICT**：每个检查点 1 个；每部分 1-3 个。
- **RECALL**：part-01 为 0；part-02 起顶部 1 个；按主要知识点边界可增加，不以字数为触发。
- **DESIGN-NOTE**：每个独立设计决策 1 个，放章节末尾；不设全部分总数上限。同一章节超过 2 个时，考虑拆章节。
- **UNVERIFIED**：不设上限；同一部分出现 ≥3 个关键事实标记时，先做一次定向补证，仍无法确认才保留。
- **宁缺毋滥只约束装饰性标注**（尤其是 ASIDE），不是删除必要解释、警告、类比或边界的理由。标注是强调手段，但教学信息不能被“总数上限”挤掉。

## 不变量（始终生效，与 voice 无关）

这些规则在**每种** voice 和**每个**写作操作中都成立：

- **有据可依或标记——绝不虚张声势。** 每个关键声明有来源或 `[!UNVERIFIED]` 标注。
- **在陷阱发生前命名它们。** 使用 `[!HEADS-UP]` 警告即将踩坑的内容。
- **先展示错误版本，再展示修复。** 演示诱人但有问题的方法，然后展示修复。
- **定义术语，然后给出内行名称。** 粗体标记规范术语，同义词紧随。
- **使用领域真实名称。绝不用 `foo`/`bar`。**
- **每次都用具体数字。** "48000"比"很快"更有记忆点。
- **指定异常输入。** 引入处理器后，立即回答"几乎匹配但不完全匹配的输入会怎样？"
- **在关键事实首次出现时内联引用。** 深度链接到具体章节，而非首页。

**优先级绝对——不变量获胜。** voice 仅控制语气；绝不放松准确性、研究、引用或验证规则。

## 先研究（起草之前）

在写下任何一句话之前，**先去阅读**。使用网络搜索和抓取工具找到该主题的权威来源——官方文档、规范/RFC、原始论文、源代码、知名的深度文章。不要从记忆中重建。

**检索预算（生成与续写统一；按 `topic_novelty` 取「配额矩阵」中的数值）：**

| 项目 | 规则 |
|------|------|
| 搜索调用 | familiar 3 / adjacent 5 / new 8 次；**1 次调用可携带 1-4 条 query**，计调用不计 query |
| 定向全文抓取 | familiar 1-2 / adjacent 3 / new 5-6 次；仅当摘要不足以支撑某个关键事实时执行 |
| 抓取下限 | 无；摘要够用就 0 次 |
| 来源条数 | **不设上限**；`## 来源` 超过 5 条按主题分组 |

**分级执行：** 先用 1-2 次搜索（可各带多条 query）建立事实骨架；只有当某个关键事实（精确 API / 函数签名、默认值、标志名、版本号、采样率、页面大小、语义保证、错误信息）的摘要不完整时，才升级为定向抓取。每次抓取前写下要回答的一个问题，只提取相关章节。

**来源下限（所有新颖度都适用）：** 每个部分至少打开/确认 **3 个实际来源**，其中至少 **1 个官方/一手来源**（官方文档、规范/RFC、源代码、官方 changelog）。**搜索调用数不等于来源数**；如果 3 次搜索只拿到摘要，必须为关键事实升级为定向抓取。关键事实必须由已打开/确认的来源支撑；只有摘要、没有原文的精确 API/默认值/版本号，不得直接写成确定事实。

**来源优先级：** 官方文档/规范/RFC/源码/changelog > 高质量独立文章/论文 > 博客/问答。关键事实不能只依赖最后一类；独立文章用于解释、对比和补充，需与官方来源交叉。博客/问答只能作为线索，不能作为唯一依据。

**关键事实覆盖表（内部记录或 `research.md`）：** 列出本部分要断言的关键事实（API/签名、默认值、版本、限制、错误行为）→ 来源 → 用在哪一节；每个关键事实至少一个来源，没有来源就标 `[!UNVERIFIED]`。不要只查“概念”而漏掉关键 API。

> **"研究充分"的判据是"每个关键事实都有来源或已标记 `[!UNVERIFIED]`"，不是"抓了 N 个页面"。** 少抓不是放宽，多抓也不等于尽责。

- **摘要优先，按需深读：** 先从搜索结果的标题与摘要中提取事实，只在摘要不够时才抓全文。
- **一搜多问：** 一次搜索调用可带 1-4 条 query，把同一主题的不同角度一次问出；不要用 4 次调用问 4 个相邻问题。
- **针对性抓取：** 全文抓取时带上明确的问题（如"`comptime` 的零开销保证"），只提取相关章节，避免整页内容进入上下文。
- **为关键事实而阅读：** 精确的 API/函数签名、默认值、标志名称、版本号、采样率、页面大小、语义保证、错误信息、历史声明。在每个事实旁记录 URL——深度链接到具体章节或锚点。
- **让行文基于所读而非所忆。** 当来源与记忆矛盾时，来源获胜。找不到来源的关键声明用 `[!UNVERIFIED]` 标记。
- **保留查阅过的 URL 列表。** 内联引用关键来源，在 `## 来源` 中列出，并记录到 `metadata.json` 的 `sources`。来源数量不设上限；>5 条按主题分组。
- **续写时不重复研究已覆盖内容：** 只研究**本部分新引入**的内容；已有部分建立的事实直接沿用，不再重新查证。**同一教程的后续部分先复用 `metadata.sources` 与 `continuity.fixed_numbers`；跨多部分的新主题可用可选 `research.md` 记录"事实 → 来源 → 用于哪一部分"，避免重复检索。**
- **`[!UNVERIFIED]` 是研究信号：** 同一部分出现 ≥3 个关键事实标记时，先做一次定向补证；仍无法确认才保留标记。
- **没有网络工具？** 用一句话告诉用户，然后更保守地写作：减少精确数字的断言，对关键未知项使用 `[!UNVERIFIED]` 标记。

## 预检（私下进行，不让用户审批；唯一例外见 knowledge-ledger.md「写前计划确认」）

在写下任何一句话之前，在脑中确定：

> **本步只做"写前决策"，不做核对。** 写后核对见文末"交付前自检"——两者分工不重复：预检产出"写什么"（示例、数字、隐喻、寄语、练习方向），自检负责六项讲透、代码完整性、结构与数量核对。**来源的查阅属于上方"先研究"，此处不重复确认。** 示例、数字、隐喻等写法决策不交给用户审批；**只有知识点计划**在满足 knowledge-ledger.md「写前计划确认」的触发条件时发给用户确认。

- **版本-特性一致性。** 示例代码使用的语法/特性/API 在锁定的工具链版本下成立；配置代码块（如 `Cargo.toml` 的 `edition`、依赖版本）与锁定版本一致。不确定特性的引入版本时查官方 changelog，绝不凭记忆断言——这类冲突（如 edition 2024 配 2021 语义的代码）应在写作时拦截，而非留到验证或读者手中。
- **控制性示例。** 选择一个具体的产物并贯穿始终。如 *"一个 4 声部减法合成器演奏持续的 A 小调三和弦"* 或 *"一个名为 `pebble` 的键值存储，能在 `kill -9` 后存活"*。不要中途切换。续写时从 `continuity` 摘要读取，精确复用。
- **具体数字。** 采样率、缓冲区大小、页面大小、表基数、延迟预算——领域提供的任何参数。
- **知识点范围。** 本部分准备讲几个主知识点？**构建名额 4-7 个**（每章 1 个，紧耦合最多 2 个但总数 ≤7；**地基章节与 §0 承接章节不消耗这 4-7**，只计入「地基 + 承接 + 构建 ≤9」）；backlog 还债条目按「名额分配」表占用构建名额。**用户给了清单时先归一化，再按knowledge-ledger.md「知识点来源」的名额分配决定本部分讲哪几条**；装不下的写进 `knowledge_backlog`（不是 `next_hook`，它会被覆盖）。满足「写前计划确认」触发条件时，把这份计划发给用户、拿到回复再动笔。不要压缩每个知识点。
- **代码完整性。** 本部分是否修改现有 API/签名/跨文件接口？若是，先计划改动面表（文件、符号、改什么、调用点）和至少一个集成检查点；代码块准备标成 `runnable` / `fragment` / `exercise`，不以行数裁剪。
- **练习承接分流。** 读上一部分的 `## 练习`，把**引入新概念的必做题**（≤2 道）逐题按三档判定（档 1 融入 / 档 2 承接章 / 档 3 顺延）；选做题不分流。档 2 要在 `## 前置条件` 之后留一个承接章节（≤2 条）；档 3 写进 `knowledge_backlog`，**并在正文留提醒**（题面斜体 / 承接章末尾 / 本部分不覆盖）。旧教程的上一部分若有超过 2 道引入新概念的必做题，照旧逐题分流，不回改旧部分。
- **地基章节（new/adjacent/beginner）。** 先判断本部分是否需要地基章节：`new` 可 1-2 个、`adjacent` 可 0-1 个、`beginner` 可 0-1 个；`familiar` 默认 0 个。每个都要直接服务于后面的构建章节，并带一个可观察/可运行的小例子。若不需要，明确写 0 个，不要为凑数加。
- **一个控制性隐喻（可选但有力）。** 一座山。一条流水线。一间厨房。至少三个章节过渡中使用，然后*明确告别它*。
- **结尾寄语。** 你希望读者准备好在你教的内容*之外*做什么？
- **练习方向。** 定下**必做 3-5 个 + 选做 0-3 个**的练习方向（每个具体到有动力的读者可以在 30 秒内开始）；**必做题中引入新概念的最多 2 道**，选做题引入新概念须附线索与官方文档入口；**数量核对归自检**。新主题至少包含一个"照着改"和一个"从零复现/预测-验证"的必做方向。

## 风格标杆与主锚点

voice 控制语气，**风格标杆控制写作节奏和结构选择**。每个教程锁定**一个主锚点作者**，记录在 `metadata.json` 的 `style_anchor` 字段。

- **生成时：** 按 `<SKILL_DIR>/SKILL.md`「风格主锚点速查」表匹配主锚点，将其 id（如 `nystrom`、`amit-patel`）写入 `style_anchor`。**只选 id 时不读 `style-benchmarks.md`**；仅当需要理解该锚点的具体写作手法时才读它的「标杆作者」表。
- **续写/复习时：** 直接从 `metadata.json` 读取 `style_anchor` 并沿用，**不再读取 style-benchmarks.md**。字段缺失的旧教程：按已有部分的实际写作节奏推断一个 id，本次写回 metadata 时补上（仅此一次需要读 style-benchmarks.md）。

主锚点指导三件事：章节如何组织（Nystrom 式独立成篇 vs Ciechanowski 式逐层拆解）、代码演示的节奏（Amit Patel 式渐进可运行 vs Sam Who 式精炼配可视化）、与读者的距离（Julia Evans 式亲切聊天 vs plainspoken 式精确陈述）。

**主锚点控制节奏和结构，不覆盖讲透原则。** 当某锚点的“精炼/少即是多”与六项讲透冲突时，讲透优先；精炼是节奏，不是删解释的理由。

## voice 的应用

- **plainspoken**（默认）—— 直接、精确，坦承由机器生成；平实散文，语气精确；短句是风格，不是解释长度上限，复杂解释可以用长句。不虚构人格。**默认情况直接按本行摘要写作，不要读取 voice.md。**
- **companion / craftsman** —— 仅当 `metadata.json` 的 `voice` 字段为这两者时，才读取 `<SKILL_DIR>/references/voice.md` "内置 voice"一节获取完整规范（单一事实源）。
- **自定义 voice** —— 读取 `<TUTORIALS_DIR>/voices/<名称>.md` 获取规范。

续写时**不重新选择 voice、不漂移**——从 metadata 读取并沿用。

## 内容与教学法

以下是不变量的落地写法示例。

**内联引用——对比：**
> ❌ "Zig 的 `comptime` 在编译时运行代码，产生零运行时开销。"
> ✅ "Zig 的 [`comptime`](https://ziglang.org/documentation/master/#comptime) 在编译期间运行普通 Zig 代码。结果被作为静态数组烘焙进二进制文件——[零运行时开销，这是语言保证](https://ziglang.org/documentation/master/#comptime)。"

**预测节拍——对比：**
> ❌ *（无预测；读者冷启动运行命令）*
> ✅ `> [!PREDICT]` *运行之前：正弦表有 1024 个条目。`@sizeOf(@TypeOf(sine_table))` 会输出什么？*
> *（答案——4096 字节——更有冲击力，因为读者先承诺了一个数字。）*

**间隔检索——对比（第 N≥2 部分开头）：**
> ❌ "在第 2 部分我们将添加滤波器。先快速回顾……"
> ✅ `> [!RECALL]` *继续之前快速回忆：`write_pos % BUFFER_SIZE` 实现了什么？*
> *（读者必须重建答案——检索会加强记忆。）*

**渐隐脚手架——对比：**
> ❌ "现在添加 Release 阶段："*（后面是完整写好的代码块）*
> ✅ "你已经看到 `Attack` 如何在 `attack_samples` 内从 0 斜升到 1。`Release` 做镜像——现在用相同循环形状写出来。"

**结尾反思——对比：**
> ❌ "做得好！你构建了……"
> ✅ "用两句话说明，为什么环形缓冲区在这里优于 `sync.Mutex` 保护的切片？"

### 概念锚定——从已知知识引申

介绍重要概念时，除了详细介绍本身，还要**从读者已知的知识体系出发引申讲解**，让新概念锚定在旧知识上。锚点按 `metadata.json` 的 `experience_level` 字段选择（生成时询问并写入，续写时读取——不要重新询问）：

- **`beginner`** → 用日常生活经验或最基础的编程概念做类比；
- **`familiar`** → 类比本领域相邻的已知概念；
- **`experienced`** → 直接对照读者熟悉的其他语言/系统机制，指出对应关系与差异。

字段缺失的旧教程：按已有部分实际使用的类比深度推断，本次写回 metadata 时补上。

**对比：**
> ❌ "所有权是 Rust 管理内存的机制：每个值有唯一所有者，所有者离开作用域时值被释放。"
> ✅ "如果你写过 C++，可以把所有权理解为'编译期检查的 `unique_ptr`'：每个值有唯一所有者，所有者离开作用域时资源自动释放——Rust 只是把这项检查从运行时移到了编译期，零运行时开销。"

**术语定义与类比锚定分开处理：**

- **术语定义：** 本部分所有新术语首次出现时，用粗体标记规范术语，先给一句话结论，必要时展开前置知识、与读者熟悉概念的对照。不设数量上限，也不设句数上限。
- **类比锚定：** 只对"最难理解/最容易误解"的概念做类比。每个难概念 0-1 个，不设总数上下限，不硬造；要讲清映射、差异/失效边界、如何回到精确术语。需要几句就几句，需要表格就用表格。`beginner` / `new` 至少为最难的概念提供一个锚点（覆盖要求，不是数量要求）。
- 类比只是桥梁——搭上桥后必须回到本语言的精确术语；类比失效处（行为有差异）用一段话或 `[!NOTE]` 点明，不设句数上限。
- 不要为每个术语强行类比；定义清楚比类比更重要。

**常见误解：** 对最容易误解的概念，写清“常见误解 → 为什么错 → 正确心智模型”。不要只给 `[!HEADS-UP]` 警告却不解释误解；可以放在概念锚定或章节末尾，不必新增小节。

## 旁白和设计笔记

**旁白** —— 装饰性、内联，保持简短（通常一两句，但不设硬句数）。词源、故事、"顺便说一句"；不承担教学功能。
```markdown
> [!ASIDE]
> "Lex" 来自希腊语 *lexis*，意为"词语"。
```

**设计笔记** —— 多段落的关于*为什么是这样*的岔开讨论。每个独立设计决策 1 个，放在章节**末尾**，绝不在步骤中间；不设每章 1 个的硬上限。同一章超过 2 个时，考虑拆章节。
```markdown
> [!DESIGN-NOTE]
> **为什么用环形缓冲区而不是通道？**
> 关于替代方案的几句话……
```

## 视觉元素

图表按机制需要，不设总数上限；仅在某个时刻确实受益时使用，一张图只表达一个机制。工具：

## 代码

- 每个代码块前一句话，告诉读者先看什么。
- **代码长度由完整性决定，不设行数上下限。** 完整可运行的代码可以很长；不得为了行数拆碎、省略或删掉 `use`、错误处理、关键类型标注。
- **新写代码块应标明类型**（写在代码 fence 的 info string，紧跟语言名，如 `rust runnable`；类型词之后可附加 `file=` 等属性，verify 目前不解析，接缝仍以前文说明为准；未标记按 `runnable` 兼容旧教程，图表语言 `mermaid` / `plantuml` / `dot` 未标记时视同 `text`）：
  - `runnable`：完整可运行/可编译的单元；verify 会执行。
  - `fragment`：片段；必须在前文明确写出它属于哪个文件、插在哪里、与哪些块组合。verify 不单独执行。
  - `exercise`：练习/填空；必须提供参考答案或检查方式。verify 不执行。
  - `text` / `output`：非执行文本（预期输出、文法、文件树、日志、树形）。verify 跳过，不占步骤号；不要用它们伪装可运行代码。
  - `expected_failure`：故意失败的命令/示例；verify 会执行并期望非零退出或预期错误。前文必须写明预期退出码/错误信息；意外成功记为失败。它占可执行步骤号。
- 同一文件的完整代码如果被拆成多个 `fragment`，必须另外提供一个覆盖最终状态的 `runnable` 块或检查点；verify 不自动拼装 fragments，也不把 `exercise` 当完整代码执行。
- **大代码块优先拆成多个完整块。** 单个 `runnable` 超过约 100-120 行时，按文件/逻辑段拆成多个完整 `runnable` 块（如 tokenizer、AST、parser、main、tests），每块前说明它是同一文件的哪一段。不要用一个巨大块，也不要删代码；如果保留完整文件作为参考块，放在最后并说明“前面已分段看过”。
- **测试单独成块。** `#[cfg(test)]` 测试可以单独成一个 `runnable` 块（或依赖主文件的 `fragment`），并说明运行命令；不要把实现和测试塞进一个 300 行的大块。
- **运行必需代码不得用 `...` 省略。** 与本节无关的样板若必须省略，放在 `fragment` 块并标明文件/位置；`runnable` 块中不要出现 `...`，出现即视为代码不完整。
- **修改现有 API/签名时，给出改动面表：**

  | 文件 | 符号 | 改什么 | 调用点是否已更新 |
  |---|---|---|---|

  代码块自身可运行 ≠ 项目可运行；跨文件改动必须列出所有调用点，或写明“无需改”的理由。每个有代码改动的部分至少有一个集成检查点（编译/类型检查/启动/端到端）。
- **修改时，指明接缝：** *"在 `process_buffer` 内部，紧接 voices 循环之后："*。
- **渐隐脚手架：** 第一个代码块完整展示。最后一两个切换为填空模式，标为 `exercise`，并提供参考答案或检查方式；不要把 `exercise` 当 `runnable` 验证。

## 交付前自检（写完之后，落盘之前）

**核对方式：逐节进行，计数/查找为主，不要重读全文。** 每写完一个 `## ` 章节，就地检查该节的知识点六项、标注用途、代码块类型与接缝；全文写完后只做下面这些**跨章节**的项。

**自检效率（硬性流程，避免反复通读）：**

- 每节只做一次六项检查，记一行结论；不要在全文写完后重新通读整篇找问题。
- 最多两轮：第 1 轮逐节六项；第 2 轮只查跨章节项和已发现问题的修复点。**不要第三轮全文通读。**
- 发现多处问题时集中一次修完；修复后只复查受影响的行/块，不重新扫描全文。
- 自检表只留在内部，不写进教程正文；给用户的回复只报告修正项，**外加公开「覆盖回执」**（格式见 knowledge-ledger.md「播报与覆盖回执」）。

### 交付前试跑与脚本检查（有 shell 时必做）

读代码发现不了「编译不过」「跑出来是反的」「回执数字填错」——真实验证里一次生成 19 个 `runnable` 块有 5 个有缺陷（1 个编译通过、输出看着有序、结果完全相反），回执里的章数也填错过。所以落盘前**真的跑一遍**，并用技能自带脚本做机械检查：

```text
python3 <SKILL_DIR>/scripts/part_lint.py   <教程目录>/part-NN.md          # 结构、代码块类型、练习上限、实写章数
python3 <SKILL_DIR>/scripts/trial_run.py   <教程目录>/part-NN.md --run    # 逐块编译/运行 runnable 与 expected_failure
python3 <SKILL_DIR>/scripts/ledger_check.py <教程目录> --receipt part-NN.md  # 写回账本后对账，输出回执行
```

- **在哪跑**：系统临时目录（`trial_run.py` 自建、跑完删除）。**不用** `.lathe-verify/`，**不碰**用户项目与 `local_project_path`。
- **本部分没有 `runnable` / `expected_failure` 块**（总结部分、纯推导部分）：脚本会打印「本部分没有 runnable / expected_failure 块，无需试跑」，回执那一行照抄它。**不要写成「0/0 通过（已运行)」**——那会被读成「验证过了」。
- **脚本跑不了的部分手动补**：标「需拼工程」的块（依赖前文代码或外部依赖）与 `## 检查点` 命令，按正文插入说明在同一个临时目录里拼出工程再跑（part-02 起从上一部分「本部分结束时的文件状态」起步）；检查点实际输出与正文预期逐行比对，**数字以实际运行为准改正文**。
- **护栏同 `/lathe 验证`**：不 `sudo`、不全局安装、不写临时目录之外的文件；允许依赖下载。
- **不是验证**：不写 `verify-result.json`、不改状态横幅与 `metadata.status`。
- **脚本只跑本次新写/改动的部分**——0.6.0 之后新增的约束（档 3 提醒写积压 ID、引入新概念的必做练习 ≤2）对更早版本写的历史部分是误报，检查历史部分时加 `--legacy`，其结果只作参考、不算交付失败。

**跑不了**（无 shell / 无工具链 / 需外部服务 / 拼工程成本明显超过本部分篇幅）：不阻塞交付，回执里写明哪些没跑、为什么；脚本也跑不了时按下面 1-10 项与 knowledge-ledger.md「人工核对清单」逐条核对。
- 任何脚本退出码非 0 都先修再交付；改不通的块不得标成 `runnable`。回执的「试跑」「实写 N 章」「本部分覆盖」「账本」行直接粘贴脚本输出。

1. **知识点覆盖（六项讲透）**：每个构建节列出它的主知识点（可合并章是 2 个，**两个都要各自过六项**）；检查定义、动机、用法、例子、边界、可观察的验证结果。缺项就补内容或减少知识点，不靠删减合规。列出“知识点 → 章节 → 六项证据”的映射（其中「知识点 → 章节」部分即覆盖回执）；每个核心知识点至少有一个练习或可观察结果（可在检查点/正文验证句中覆盖）。
2. **讲解手段**：难概念是否有类比/对照（按需，不按数量）；类比是否讲清映射和失效边界；术语是否结论先行、按需展开；有常见误解的难概念是否写了“常见误解 → 为什么错 → 正确心智模型”（不必新增小节）。
3. **标注用途（不数总数）**：每个 HEADS-UP/NOTE/TIP 对应哪个知识点/真实陷阱？ASIDE 是否 ≤2？有没有装饰性标注？**不要为了数字删除真实警告或必要补充。**
4. **代码完整性（查找比对）**：每个代码块是否标了 `runnable` / `fragment` / `exercise` / `text` / `output` / `expected_failure`？`runnable` 是否完整可运行？是否有未解释的 `...`？`fragment` 是否写明文件和接缝，且被最终 `runnable`/检查点覆盖？`exercise` 是否有答案/检查方式？故意失败的命令是否标成 `expected_failure` 并写明预期退出码/错误？改动面表是否完整？集成检查点是否存在？**单个 `runnable` 超过约 100-120 行时，是否按文件/逻辑段拆成多个完整块呈现（分段，不是裁内容）；测试是否单独成块或说明接缝。** **交付前试跑是否做了**（`trial_run.py` + 手动补跑检查点）；`part_lint.py` 是否通过。
5. **结构与知识点数量**：对照结构变体表，`##` 小节齐全、顺序正确；构建 4-7、每章 1 个主知识点（紧耦合最多 2 个但总数 ≤7）；地基 0-2；**承接 0-1**；**地基 + 构建 + 承接 ≤9**（超 9 时减构建条数并写入 `knowledge_backlog`，不减地基与承接）；**本部分结束状态（文件/符号/命令）、下一部分起始状态（文件/函数/命令/未完成项）和非目标是否写清**；**是否需要拆部分只按「独立学习里程碑 / 独立改动面 / 一次学习 session 能否走完」判断，不按字数判断**——篇幅长不是缺陷，不得为控制篇幅压缩解释。
6. **练习/来源/版本/术语/一致性**：必做 3-5、选做 0-3、总 ≤8；来源只列正文引用过的，且至少 3 个实际来源（至少 1 个官方/一手）；版本与 `tools` 一致；新术语都有定义；**代码中的符号/数字/API 与正文、`fixed_numbers` 一致**。
7. **索引**：`continuity` 是否同时满足「各字段条数上限」与「2200/3000 字预算」？跑 `ledger_check.py <教程目录> --continuity` 看实测。超出时归档到 `research.md` 对应小节，**不压缩正文**（预算可达是靠条数上限保证的，不是靠把摘要写得更短）。
8. **知识点、积压、练习承接与账本**：有 shell 时 `ledger_check.py` 与 `part_lint.py` 都通过（`ledger_check.py` 会抓 `已承诺未兑现`——上一部分答应要讲却没讲的条目不允许留在 `planned`）；没有 shell 时按 knowledge-ledger.md「人工核对清单」六条逐条核对。两种情况都要确认：写前计划里的每一条在回执与账本里都有着落、计划章数 = 实写章数、没有条目被删除或被模型自行改成 `self-study` / `dropped_by_user`。

**超限处理顺序（不要机械删除）：**

1. 先删/合并 **ASIDE**（装饰性旁白），它们不承担教学功能。
2. 信息型标注如果重复，合并同一章节的同类提醒；能进正文散文的长解释就进散文，但不因“总数”删掉真实陷阱。
