# 写作核心

本文件是 Lathe **写作型操作**（生成、续写、复习、收尾、面试文档）共用的单一事实源（教程结构、配额矩阵、标注、不变量、研究纪律、预检、自检）。仅这些操作需要读取；提问、标签、列表、扫描、验证等操作不加载本文件。

`<SKILL_DIR>` 指 SKILL.md 所在目录；`<TUTORIALS_DIR>` 指默认基础目录。辅助文件布局统一按 metadata.md 解析：新课程全部在 `_lathe/`，legacy 全部留在根目录；混合布局停止写入。所有脚本命令都传**课程根目录**。

## 教程结构（单一事实源）

每篇教程（或系列的每个部分）遵循此结构，但章节*标题*必须特定于领域：

```
# [标题]

[引子——按需，建议 1-4 段；以建立问题和动机为准，不设段数上限]

## 你将构建什么
一段或几段。用控制性示例命名的具体最终状态。

## 前置条件
列表：需要安装的工具、读者应大致了解的知识。

## [可选：0-2 个地基章节——心智模型/术语/环境]   ← 按配额矩阵的地基额度；不计入构建配额
为什么需要先建立这个地基。一个可观察或可运行的小例子。不引入后文不会用到的概念。

## [可选：0-1 个承接章节——上一部分练习留下的问题]   ← 按配额矩阵的承接额度；不计入构建配额
把上一部分练习里引入、与本部分知识点没有交集的概念集中讲掉。
放在这里而不是检查点之后：读者应该在开始动手前就知道欠账在哪。
每条都要讲透（定义 + 如何解释当时的疑问 + 1 个可运行验证），常见 150-400 字，**不设字数上限**。

## [具体的章节标题——命名本章节创造的东西]
为什么需要它。小块代码，每块标注插入位置。旁白或设计笔记。
（按配额矩阵的构建/地基/承接配额与总章上限；候选不足 4 时不凑数。每章通常 1 点，紧耦合可 1 章 2 点）

## 检查点
> [!PREDICT]   ← 每个检查点 1 个
> 运行之前：你预期会看到什么输出？
**运行以下命令验证：** + 预期输出 + 可能的错误

**本部分结束时的文件状态：** 用列表或一两句话列出新增/修改的文件、关键符号、可运行命令或产物；不新增 `##` 小节。

**下一部分起始状态：** 在 `## 接下来` 中至少写明：文件、函数/符号、可运行命令、尚未完成项。

**本部分不覆盖：** 用一句话说明本部分明确不解决什么。若有未选知识点，按知识表 ID 点名并写“留在池中、后续优先”；不要用含糊的「以后再讲」，也不要预测具体 Part。

**练习承接：** 按三档写本部分练习引入的新概念去向（无则写「无」），并单独交代上一部分到期承诺是否兑现：
- 档 1 融入：`<ID 知识点>` → 本部分 §X（三件套：疑问复述 + 解释 + 可运行验证）
- 档 2 承接章：`<ID 知识点>` → 本部分 §0
- 档 3 顺延：`<ID 知识点>` → 知识表 `queued`，后续优先；题面另加斜体提醒
- 上一部分承诺：`<ID>` → 本部分已讲透（§X）／未讲成，已顺延 Part N

## 接下来
寄语或前向钩子：最后部分邀请读者走出铺设的道路；非最后部分按需要命名 1 个或多个未决问题。随后用平实散文提出**结尾反思**：挑最重要的设计决策，要求读者解释*为什么*而非*是什么*，不替他们回答。`next_hook` 只承载衔接语境，不承载知识点状态。

## 练习（必做编号 3-5 个 + 选做 0-3 个，总 ≤8；每个具体到 30 秒内可开始）
**必做题最多 2 道引入本部分没讲过的新概念**，其余只用已讲内容；新概念按 knowledge-ledger.md「练习承接与承诺门禁」进入知识表（`来源=exercise`、`类型=carry`）。
档 3 题面后写：*本题涉及的知识点（X，池中 ID `K`）不在本部分展开，后续优先讲。* 实际讲到时在章节开头回指来源。
**选做题可以引入新概念，但每道必须附「线索 + 官方文档入口」**；默认不进知识表。用户之后想系统学时，再按普通清单条目提出。

## 来源（编号，格式：[标题](url) —— 一句话说明；数量不设上限，超过 5 条按主题分组）
```

每个部分以 *"在本部分结束时，你将拥有 [具体的东西]"* 开头，以检查点结尾。每个部分独立成篇。

**写作时按下方「配额矩阵」控制范围，不要等写完再删。**

> **配额只约束讲几个知识点，不约束每点讲多少。** 用户新增、到期承诺、queued 与 planned（按行序）只要属于构建知识点，就共同使用构建名额；地基与承接使用各自额度，并共同受总章上限约束。候选不足 4 时不凑数。
>
> 每点按定义、动机、用法、例子、边界、验证六项讲透。装不下时减少本 Part 的点或拆 Part，不压缩解释。

只按结构判断超出：知识点超过配额；章节总数超过配额矩阵的上限或单章超过 2 个独立点；一个最终检查点无法覆盖完成标准；代码需要多个独立集成里程碑；一次交付或学习 session 无法完整走完。任一成立就按知识点边界拆 Part，或把未选中的行留在池中保持 `planned` / 改为 `queued`；不要写进 `next_hook`，不要在 `course_plan` 放点级补项，也不要把点预分配给某个 Part。

**篇幅与行数不是上限。** 正文约 10,000 中文字符、单个 `runnable` 约 100–120 行都只是观察信号；里程碑无需拆时继续写。大代码块按文件或逻辑段分成完整块，不裁内容。索引超限只修剪可重建缓存，不压缩正文。

**一个知识点**是读者能用自己的话解释，并在代码、命令或推导中复现的单一概念或技能。章节通常 1 点，紧耦合可 2 点，但每点分别计数并讲透。

**按操作的结构变体（登记在此，不在别处另行定义）：**

| 操作 | 结构差异 |
|------|----------|
| 生成 part-01 | 如上，无 `[!RECALL]` |
| 续写 part-NN（N≥2） | 顶部加 `> [!RECALL]` 节拍；`## 接下来` **之前**插入 `## 目标达成回顾`；上一部分有档 2 时，在 `## 前置条件` 之后加承接章节（≤1 章、≤2 条） |
| 收尾 part-NN（总结部分） | 必备七节：`全课程回顾` / `知识图谱` / `目标对照` / `未讲清单（按 ID）` / `回顾自检`（代替 `## 检查点`）/ `练习方向` / `寄语`。若仍有 `planned`/`queued`，H1 后必须加「完成状态：未学完」提示并列出剩余 ID 与续写入口。**不写** `## 检查点`、`## 你将构建什么`、`## 前置条件`、`## 来源`、四个契约行（没有下一部分可交接）与验证状态横幅（它永不参与验证）。逐节内容与收尾流程见 finish.md；`part_lint.py --kind finish` 按这张表检查 |
| 复习 part-NN-review | 完全独立的回顾结构，不遵循上表（详见 review.md） |
| 面试文档（复习/生成/续写产出的附加文件） | **完全独立的问答结构，不遵循本表**；**只对教学部分产出**（定义见 `interview.md`，此处不复述）。本文件对其**仅**提供「配额矩阵中的检索预算」与「有据可依或标记」不变量，**不提供**结构、标注规则与交付前自检 |

## 配额矩阵（单一事实源）

所有**知识点数量**、表达预算和流程预算集中在这里。其他模块只引用本表，不再重复数字。

**主题新颖度 `topic_novelty`**（写入 `metadata.json`）：

| 取值 | 含义 | 生成时默认推断 |
|------|------|----------------|
| `new` | 读者/模型对该主题几乎没有可靠先验，需要先建立地基 | `experience_level = beginner` |
| `adjacent` | 有相邻领域经验，核心概念可类比，具体 API/版本仍需查证 | `experience_level = familiar` |
| `familiar` | 已有同主题教程或 `sources` 覆盖，主要是复用与增量 | `experience_level = experienced` |

> 用户可在生成时覆盖默认推断。续写读取 metadata；字段缺失时按 `sources` 与知识表已讲点推断，默认 `adjacent`。无法判断时按更高新颖度处理（`new` > `adjacent` > `familiar`）。

### 1. 知识点配额（真正的范围控制）

| 项目 | 规则 | 说明 |
|------|------|------|
| 正文构建知识点 | 4-7（候选不足 4 时不凑数；无待处理时默认 4-5） | `main` / `mergeable`；每章通常 1 点，紧耦合可 2 点但总数 ≤7。只有确实没有更多候选时才少于 4，且不得用空章或拆分凑数 |
| 地基章节（豁免） | new 1-2 / adjacent 0-1 / beginner 0-1 / familiar 0 | `foundation`；不占构建 4–7，但计入总章 |
| 承接章节（豁免） | 0-1（≤2 条） | `carry`；不占构建 4–7，但计入总章 |
| 章节总数 | ≤9 | 地基 + 承接 + 构建 ≤9；超出时先减少构建选点或拆 Part，不删除前置欠账 |
| 用户显式清单 | 以归一化结果为准 | 来源三选一、优先级与溢出处理见 knowledge-ledger.md |
| 必做练习 | 3-5 | 最多 2 道引入新概念；按三档进入知识表，其余为巩固型 |
| 选做练习 | 0-3 | 默认 0；总计 ≤8；新概念附线索与官方入口，默认不入知识表 |
| 术语定义 | 全部新术语 | 不设数量上限；定义本身不是额外知识点，除非形成独立可复现产出 |
| 课程路线图 | 2-12 项 | metadata 的 Part 级路线，不承载点级状态；2 项只用于确实只需两次学习 session 的小课程 |

**配额是范围，不是目标。** 无用户新增、到期承诺或 `queued` 时按配额矩阵的默认目标；存在这些条目时按构建名额上限。选点严格采用 knowledge-ledger.md 的硬优先级；未选中的点留在池中 `planned` 或改为 `queued` 并留延后提醒，不压缩解释。**少于 4 点只在候选确实耗尽时允许；还有未选候选就必须补足或说明为什么不留。**

### 1b. 外部清单深度（做 / 讲 / 知）

当知识表 `备注` 含 `深度=做|讲|知` 时，按该点要求的教学深度执行，而不是一律扩成完整构建章：

| 深度 | 写作标准 | 结构落点 |
|---|---|---|
| `做` | 定义、动机、用法、例子、边界、可运行验证六项；有新增实现和练习 | 通常为 `main` 构建章，占构建名额 |
| `讲` | 定义、机制、取舍、适用/失效边界、一个可观察例子；不强制新增完整实现，可复用已有代码或输出 | 通常为 `main`；仍占构建名额，但篇幅按机制需要 |
| `知` | 是什么、何时用/不用、与本课的关系、官方入口；要求被问到能答方向 | 优先与相邻构建点同章（`mergeable`）；确属前置背景才用 `foundation`，不写 `carry` |

- `知` 不是“可以不讲”：仍须在正文有可定位的 `at:` 章节，只是不要求独立完整实现。
- `讲` 和 `知` 不得被自动升格为 `做`；也不得为了压篇幅删掉例子、边界和验证。
- 没有 `深度=` 的普通知识表条目沿用默认“六项讲透”。
- 多个深度混排时，构建配额按 `main` / `mergeable` 计；`知` 若标为 `foundation` 则按地基章节额度。

### 2. 表达与索引预算（按需，不作为讲透门禁）

| 项目 | 规则 | 说明 |
|------|------|------|
| 引子 | 建议 1-4 段 | 不设上限；以建立问题和动机为准 |
| 你将构建什么 | 一段或几段 | 讲清最终状态即可 |
| 接下来 | 按需 | 命名 1 个或多个未决问题 |
| 术语定义 | 结论先行，按需展开 | 不设句数上限 |
| 类比锚定 | 每个难概念 0-1 个 | 不设总数上下限；不硬造；讲清映射和失效边界 |
| 信息型标注（HEADS-UP/NOTE/TIP） | 按需 | 不设总数上限；每个对应具体知识点/真实陷阱 |
| ASIDE | ≤2/部分 | 装饰性旁白，保持简短；不承担教学功能 |
| DESIGN-NOTE | 每个独立设计决策 1 个 | 放章节末尾；不设每章 1 个的硬上限 |
| PREDICT | 每个检查点 1 个 | 每部分 1-3 个 |
| RECALL | part-01 为 0；part-02 起至少 1 个 | 按主要知识点边界增加，不以字数为触发 |
| 图表 | 按机制需要 | 一张图一个机制；节点 ≤12 |
| 代码块 | 由完整性决定 | 不设行数上限（单个 `runnable` 超过约 100-120 行时优先按文件/逻辑段拆块，不裁内容）；六类标记齐全：`runnable` / `fragment` / `exercise` / `text` / `output` / `expected_failure`，**未标记按 `runnable` 处理**（图表语言 `mermaid` / `plantuml` / `dot` 例外，未标记也视同 `text`） |
| 总结部分 | 不适用「构建配额 / 实写 N 章」 | 它不引入新知识点；回执那一行改写「总结七节 ✅」（`part_lint.py --kind finish` 输出） |
| 索引（continuity） | 2200 字软 / 3000 硬；字段上限见 metadata.md | 可重建缓存预算；超出修剪缓存或归档 open threads，不压缩正文；用 `ledger_check.py <课程根目录> --continuity` 实测 |

### 3. 流程预算（与正文长度无关）

| 项目 | familiar | adjacent | new | 规则 |
|------|----------|----------|-----|------|
| 搜索调用（1 次可含 1-4 query） | 3 | 5 | 8 | 计调用，不计 query |
| 定向全文抓取 | 1-2 | 3 | 5-6 | 每次抓取一个命名问题 |
| 来源条数 | 不设上限 | 同左 | 同左 | `## 来源` 超过 5 条按主题分组 |

**使用规则：**

0. **本表是权威。** 其他数字只是投影；调参时同步检查结构与自检。
1. 无待处理构建点时按配额矩阵的默认目标；有用户新增、到期承诺或 `queued` 时按构建名额上限。所有构建来源共用这一容量；地基与承接使用各自豁免额度。
2. 表达与代码不设内容上限；不要用配额压缩单点解释。
3. continuity 是缓存预算，不是正文预算；按 metadata.md 修剪，不删正文。
4. 只按知识点数量、独立里程碑、独立改动面与单次交付能力判断超出；触发时拆 Part 或减少本 Part 选点。

## 标注类型

| 标注 | 用途 | 频率 |
|------|------|------|
| `> [!PREDICT]` | 检查点前的预测提示 | 每个检查点 1 次；每部分 1-3 次 |
| `> [!RECALL]` | 第 N≥2 部分顶部的间隔检索 | part-01 为 0；part-02 起顶部 1 次；按主要知识点边界可增加，不以字数为触发 |
| `> [!HEADS-UP]` | 即将踩坑的警告 | 每个真实陷阱 1 次；**不设总数上限** |
| `> [!ASIDE]` | 词源、故事等旁白 | 装饰性；**≤2 次/部分**；保持简短，不承担教学功能 |
| `> [!DESIGN-NOTE]` | 多段落的"为什么"讨论 | 每个独立设计决策 1 次；放章节末尾；不设每章 1 个的硬上限 |
| `> [!UNVERIFIED]` | 无法确认的关键声明 | 按需；≥3 个关键事实时先补研究 |
| `> [!NOTE]` | 中性补充信息 | 按需；**不设总数上限**；每个对应具体知识点/真实陷阱 |
| `> [!TIP]` | 便捷技巧 | 按需；**不设总数上限**；每个对应具体知识点/真实陷阱 |

**使用规则：** 信息型标注（HEADS-UP / NOTE / TIP）不设总数上限，每个必须对应具体知识点或真实陷阱；ASIDE ≤2/部分，只作装饰，不承担教学；PREDICT 每检查点 1 个、每部分 1-3 个；RECALL part-02 起顶部 1 个，按主要知识点边界可增加；DESIGN-NOTE 每个独立设计决策 1 个、放章末；UNVERIFIED 按需，同一部分 ≥3 个关键事实时先补研究。**不要为了数字删除必要解释、警告、类比或边界。**

## 不变量（始终生效，与 voice 无关）

这些规则在**每种** voice 和**每个**写作操作中都成立：

- **有据可依或标记——绝不虚张声势。** 每个关键声明有来源或 `[!UNVERIFIED]` 标注。
- **在陷阱发生前命名它们。** 使用 `[!HEADS-UP]` 警告即将踩坑的内容。
- **先展示错误版本，再展示修复。** 演示诱人但有问题的方法，然后展示修复。
- **定义术语，然后给出内行名称。** 粗体标记规范术语，同义词紧随。
- **使用领域真实名称。绝不用 `foo`/`bar`。**
- **每次都用具体数字。** "48000"比"很快"更有记忆点。
- **指定异常输入。** 引入处理器后，立即回答"几乎匹配但不完全匹配的输入会怎样？"
- **在关键事实首次出现时内联引用。** 深度链接到具体章节，而非首页。

**优先级绝对——不变量获胜。** voice 仅控制语气；绝不放松准确性、研究、引用或验证规则。

## 先研究（起草之前）

在写下任何一句话之前，**先去阅读**。使用网络搜索和抓取工具找到该主题的权威来源——官方文档、规范/RFC、原始论文、源代码、知名的深度文章。不要从记忆中重建。

**检索预算（生成与续写统一；按 `topic_novelty` 取「配额矩阵」中的数值）：**

| 项目 | 规则 |
|------|------|
| 搜索调用 | familiar 3 / adjacent 5 / new 8 次；**1 次调用可携带 1-4 条 query**，计调用不计 query |
| 定向全文抓取 | familiar 1-2 / adjacent 3 / new 5-6 次；仅当摘要不足以支撑某个关键事实时执行 |
| 抓取下限 | 无；摘要够用就 0 次 |
| 来源条数 | **不设上限**；`## 来源` 超过 5 条按主题分组 |

**执行：** 先用 1-2 次搜索（每次 1-4 条 query）建立事实骨架；只有关键事实（API/签名、默认值、版本、限制、错误行为）的摘要不足时才定向抓取，每次抓取带一个明确问题，只读相关章节。**每个部分至少确认 3 个实际来源，至少 1 个官方/一手来源；搜索调用数不等于来源数。** 关键事实必须由已打开来源支撑；只有摘要的精确 API/默认值/版本号不得写成确定事实，找不到来源就标 `[!UNVERIFIED]`。**"研究充分"的判据是每个关键事实都有来源或标记，不是抓了多少页。**

**来源优先级：** 官方文档/规范/RFC/源码/changelog > 高质量独立文章/论文 > 博客/问答。博客/问答只作线索，不能作为唯一依据。

**关键事实覆盖表（内部记录或当前布局 research）：** 关键事实 → 来源 → 用在哪一节；每个关键事实至少一个来源。research 只记来源与论证，不维护自学、已讲或排队状态。

- **摘要优先、按需深读：** 先从标题/摘要提取；摘要不够再抓全文，避免整页进入上下文。
- **续写不重复研究：** 只研究本部分新内容；复用 `metadata.sources` 与 `continuity.fixed_numbers`；跨 Part 来源写当前布局 research。
- **没有网络工具：** 明确告知，减少精确断言，关键未知项标 `[!UNVERIFIED]`。

## 预检（私下进行，不让用户审批；唯一例外见 knowledge-ledger.md「写前计划确认」）

在写下任何一句话之前，在脑中确定：

> **本步只做"写前决策"，不做核对。** 写后核对见文末"交付前自检"——两者分工不重复：预检产出"写什么"（示例、数字、隐喻、寄语、练习方向），自检负责按深度讲透、代码完整性、结构与数量核对。**来源的查阅属于上方"先研究"，此处不重复确认。** 示例、数字、隐喻等写法决策不交给用户审批；**只有知识点计划**在满足 knowledge-ledger.md「写前计划确认」的触发条件时发给用户确认。

- **版本-特性一致性。** 示例代码使用的语法/特性/API 在锁定的工具链版本下成立；配置代码块（如 `Cargo.toml` 的 `edition`、依赖版本）与锁定版本一致。不确定特性的引入版本时查官方 changelog，绝不凭记忆断言——这类冲突（如 edition 2024 配 2021 语义的代码）应在写作时拦截，而非留到验证或读者手中。
- **控制性示例。** 选择一个具体的产物并贯穿始终。如 *"一个 4 声部减法合成器演奏持续的 A 小调三和弦"* 或 *"一个名为 `pebble` 的键值存储，能在 `kill -9` 后存活"*。不要中途切换。续写时从 `continuity` 摘要读取，精确复用。
- **具体数字。** 采样率、缓冲区大小、页面大小、表基数、延迟预算——领域提供的任何参数。
- **知识点范围。** 从知识表按“到期承诺 → 用户新增 → queued → planned（行序）”选择构建点；容量与总章按配额矩阵。地基与 §0 承接使用各自豁免额度。用户清单先按 knowledge-ledger.md 归一化；装不下的留在池中 `planned` 或改为 `queued`，不要写入 `next_hook`，也不要预分配 Part。触发写前确认时拿到回复再动笔。
- **代码完整性。** 本部分是否修改现有 API/签名/跨文件接口？若是，先计划改动面表（文件、符号、改什么、调用点）和至少一个集成检查点；代码块准备标成 `runnable` / `fragment` / `exercise`，不以行数裁剪。
- **练习承接分流。** 读上一部分练习与知识表 `promise:` 行，把引入新概念的必做题逐条判为融入、承接章或顺延。到期承诺硬优先；档 1 跟随并入的构建点占位，档 2 使用承接额度，档 3 在知识表写 `queued` 并在题面、承接章末或“本部分不覆盖”中按 ID 提醒。不要维护其他承接状态。
- **地基章节（new/adjacent/beginner）。** 判断是否需要地基章节；它必须服务后续构建并带可观察例子，使用配额矩阵的地基额度。若不需要就写 0 个，不为凑数添加。
- **一个控制性隐喻（可选但有力）。** 一座山。一条流水线。一间厨房。至少三个章节过渡中使用，然后*明确告别它*。
- **结尾寄语。** 你希望读者准备好在你教的内容*之外*做什么？
- **练习方向。** 定下**必做 3-5 个 + 选做 0-3 个**的练习方向（每个具体到有动力的读者可以在 30 秒内开始）；**必做题中引入新概念的最多 2 道**，选做题引入新概念须附线索与官方文档入口；**数量核对归自检**。新主题至少包含一个"照着改"和一个"从零复现/预测-验证"的必做方向。

## 风格标杆与主锚点

voice 控制语气，**风格标杆控制写作节奏和结构选择**。每个教程锁定**一个主锚点作者**，记录在 `metadata.json` 的 `style_anchor` 字段。

- **生成时：** 按 `<SKILL_DIR>/SKILL.md`「风格主锚点速查」表匹配主锚点，将其 id（如 `nystrom`、`amit-patel`）写入 `style_anchor`。**只选 id 时不读 `style-benchmarks.md`**；仅当需要理解该锚点的具体写作手法时才读它的「标杆作者」表。
- **续写/复习时：** 直接从 `metadata.json` 读取 `style_anchor` 并沿用，**不再读取 style-benchmarks.md**。字段缺失的旧教程：按已有部分的实际写作节奏推断一个 id，本次写回 metadata 时补上（仅此一次需要读 style-benchmarks.md）。

主锚点指导三件事：章节如何组织（Nystrom 式独立成篇 vs Ciechanowski 式逐层拆解）、代码演示的节奏（Amit Patel 式渐进可运行 vs Sam Who 式精炼配可视化）、与读者的距离（Julia Evans 式亲切聊天 vs plainspoken 式精确陈述）。

**主锚点控制节奏和结构，不覆盖讲透原则。** 当某锚点的“精炼/少即是多”与六项讲透冲突时，讲透优先；精炼是节奏，不是删解释的理由。

## voice 的应用

- **plainspoken**（默认）—— 直接、精确，坦承由机器生成；平实散文，语气精确；短句是风格，不是解释长度上限，复杂解释可以用长句。不虚构人格。**默认情况直接按本行摘要写作，不要读取 voice.md。**
- **companion / craftsman** —— 仅当 `metadata.json` 的 `voice` 字段为这两者时，才读取 `<SKILL_DIR>/references/voice.md` "内置 voice"一节获取完整规范（单一事实源）。
- **自定义 voice** —— 读取 `<TUTORIALS_DIR>/voices/<名称>.md` 获取规范。

续写时**不重新选择 voice、不漂移**——从 metadata 读取并沿用。

## 内容与教学法

### 概念锚定——从已知知识引申

介绍重要概念时，除了详细介绍本身，还要**从读者已知的知识体系出发引申讲解**，让新概念锚定在旧知识上。锚点按 `metadata.json` 的 `experience_level` 字段选择（生成时询问并写入，续写时读取——不要重新询问）：

- **`beginner`** → 用日常生活经验或最基础的编程概念做类比；
- **`familiar`** → 类比本领域相邻的已知概念；
- **`experienced`** → 直接对照读者熟悉的其他语言/系统机制，指出对应关系与差异。

字段缺失的旧教程：按已有部分实际使用的类比深度推断，本次写回 metadata 时补上。

**术语定义与类比锚定分开处理：**

- **术语定义：** 本部分所有新术语首次出现时，用粗体标记规范术语，先给一句话结论，必要时展开前置知识、与读者熟悉概念的对照。不设数量上限，也不设句数上限。
- **类比锚定：** 只对"最难理解/最容易误解"的概念做类比。每个难概念 0-1 个，不设总数上下限，不硬造；要讲清映射、差异/失效边界、如何回到精确术语。需要几句就几句，需要表格就用表格。`beginner` / `new` 至少为最难的概念提供一个锚点（覆盖要求，不是数量要求）。
- 类比只是桥梁——搭上桥后必须回到本语言的精确术语；类比失效处（行为有差异）用一段话或 `[!NOTE]` 点明，不设句数上限。
- 不要为每个术语强行类比；定义清楚比类比更重要。

**常见误解：** 对最容易误解的概念，写清“常见误解 → 为什么错 → 正确心智模型”。不要只给 `[!HEADS-UP]` 警告却不解释误解；可以放在概念锚定或章节末尾，不必新增小节。

## 旁白和设计笔记

**旁白** —— 装饰性、内联，保持简短（通常一两句，但不设硬句数）。词源、故事、"顺便说一句"；不承担教学功能。

**设计笔记** —— 多段落的关于*为什么是这样*的岔开讨论。每个独立设计决策 1 个，放在章节**末尾**，绝不在步骤中间；不设每章 1 个的硬上限。同一章超过 2 个时，考虑拆章节。

## 代码

- 每个代码块前一句话，告诉读者先看什么。
- **代码长度由完整性决定，不设行数上下限。** 完整可运行的代码可以很长；不得为了行数拆碎、省略或删掉 `use`、错误处理、关键类型标注。
- **新写代码块应标明类型**（写在代码 fence 的 info string，紧跟语言名，如 `rust runnable`；类型词之后可附加 `file=` 等属性，verify 目前不解析，接缝仍以前文说明为准；未标记按 `runnable` 兼容旧教程，图表语言 `mermaid` / `plantuml` / `dot` 未标记时视同 `text`）：
  - `runnable`：完整可运行/可编译的单元；verify 会执行。
  - `fragment`：片段；必须在前文明确写出它属于哪个文件、插在哪里、与哪些块组合。verify 不单独执行。
  - `exercise`：练习/填空；必须提供参考答案或检查方式。verify 不执行。
  - `text` / `output`：非执行文本（预期输出、文法、文件树、日志、树形）。verify 跳过，不占步骤号；不要用它们伪装可运行代码。
  - `expected_failure`：故意失败的命令/示例；verify 会执行并期望非零退出或预期错误。前文必须写明预期退出码/错误信息；意外成功记为失败。它占可执行步骤号。
- 同一文件的完整代码如果被拆成多个 `fragment`，必须另外提供一个覆盖最终状态的 `runnable` 块或检查点；verify 不自动拼装 fragments，也不把 `exercise` 当完整代码执行。
- **大代码块优先拆成多个完整块。** 单个 `runnable` 超过约 100-120 行时，按文件/逻辑段拆成多个完整 `runnable` 块（如 tokenizer、AST、parser、main、tests），每块前说明它是同一文件的哪一段。不要用一个巨大块，也不要删代码；如果保留完整文件作为参考块，放在最后并说明“前面已分段看过”。
- **测试单独成块。** `#[cfg(test)]` 测试可以单独成一个 `runnable` 块（或依赖主文件的 `fragment`），并说明运行命令；不要把实现和测试塞进一个 300 行的大块。
- **运行必需代码不得用 `...` 省略。** 与本节无关的样板若必须省略，放在 `fragment` 块并标明文件/位置；`runnable` 块中不要出现 `...`，出现即视为代码不完整。
- **修改现有 API/签名时，给出改动面表：**

  | 文件 | 符号 | 改什么 | 调用点是否已更新 |
  |---|---|---|---|

  代码块自身可运行 ≠ 项目可运行；跨文件改动必须列出所有调用点，或写明“无需改”的理由。每个有代码改动的部分至少有一个集成检查点（编译/类型检查/启动/端到端）。
- **修改时，指明接缝：** *"在 `process_buffer` 内部，紧接 voices 循环之后："*。
- **渐隐脚手架：** 第一个代码块完整展示。最后一两个切换为填空模式，标为 `exercise`，并提供参考答案或检查方式；不要把 `exercise` 当 `runnable` 验证。

## 交付前自检（写完之后，落盘之前）

**核对方式：逐节进行，计数/查找为主，不要重读全文。** 每写完一个 `## ` 章节，就地检查该节的知识点六项、标注用途、代码块类型与接缝；全文写完后只做下面这些**跨章节**的项。

**自检效率（硬性流程，避免反复通读）：**

- 每节只做一次六项检查，记一行结论；不要在全文写完后重新通读整篇找问题。
- 最多两轮：第 1 轮逐节六项；第 2 轮只查跨章节项和已发现问题的修复点。**不要第三轮全文通读。**
- 发现多处问题时集中一次修完；修复后只复查受影响的行/块，不重新扫描全文。
- 自检表只留在内部，不写进教程正文；给用户的回复只报告修正项，**外加公开「覆盖回执」**（格式见 knowledge-ledger.md「播报与覆盖回执」）。

### 交付前试跑与脚本检查（有 shell 时必做）

读代码发现不了「编译不过」「跑出来是反的」「回执数字填错」——真实验证里一次生成 19 个 `runnable` 块有 5 个有缺陷（1 个编译通过、输出看着有序、结果完全相反），回执里的章数也填错过。所以落盘前**真的跑一遍**，并用技能自带脚本做机械检查：

```text
python3 <SKILL_DIR>/scripts/part_lint.py <课程根目录>/part-NN.md
python3 <SKILL_DIR>/scripts/trial_run.py <课程根目录>/part-NN.md --run
python3 <SKILL_DIR>/scripts/ledger_check.py <课程根目录> --receipt part-NN.md --structure
```

`ledger_check.py` 必须传课程根目录，由脚本整体解析新旧布局。TypeScript 块：本机有 `tsx`/`tsc` 时脚本自动类型检查/运行；没有时按脚本打印的命令手动跑。试跑使用系统临时目录并在结束后删除；不用课程验证工作区，不碰用户项目与 `local_project_path`。
- **本部分没有 `runnable` / `expected_failure` 块**（总结部分、纯推导部分）：脚本会打印「本部分没有 runnable / expected_failure 块，无需试跑」，回执那一行照抄它。**不要写成「0/0 通过（已运行)」**——那会被读成「验证过了」。
- **脚本跑不了的部分手动补**：标「需拼工程」的块（依赖前文代码或外部依赖）与 `## 检查点` 命令，按正文插入说明在同一个临时目录里拼出工程再跑（part-02 起从上一部分「本部分结束时的文件状态」起步）；检查点实际输出与正文预期逐行比对，**数字以实际运行为准改正文**。
- **护栏同 `/lathe 验证`**：不 `sudo`、不全局安装、不写临时目录之外的文件；允许依赖下载。
- **不是验证**：不写 `verify-result.json`、不改状态横幅与 `metadata.status`。
- **脚本只跑本次新写/改动的部分**——0.6.0 之后新增的约束（档 3 提醒写积压 ID、引入新概念的必做练习 ≤2）对更早版本写的历史部分是误报，检查历史部分时加 `--legacy`，其结果只作参考、不算交付失败。

**跑不了**（无 shell / 无工具链 / 需外部服务 / 拼工程成本明显超过本部分篇幅）：不阻塞交付，回执里写明哪些没跑、为什么；脚本也跑不了时按下面 1-10 项与 knowledge-ledger.md「人工核对清单」逐条核对。
- 任何脚本退出码非 0 都先修再交付；改不通的块不得标成 `runnable`。回执的「试跑」「实写 N 章」「本部分覆盖」「账本」行直接粘贴脚本输出。
