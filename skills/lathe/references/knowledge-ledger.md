# 知识点账本（0.7.0 权威契约）

把课程承诺的每个知识点只记录一次。**新课程以 `_lathe/knowledge-points.md` 为唯一知识点事实源**；不得在 metadata、research 或正文中维护第二份状态清单。

0.7.0 的核心变化：**知识点不再预先归属到 Part**。知识表是一张按行序排列的池；每次生成或续写时，Lathe 根据用户需求、上次结束状态、本地代码进度、到期承诺和池中顺序，现选本 Part 要讲的点。`course_plan` 只是 Part 级叙事大纲，不是知识点的容器，也不是选点门禁。

调用脚本时始终传**课程根目录**，不要传 `_lathe/`：

```text
python3 <SKILL_DIR>/scripts/ledger_check.py <课程根目录> [--receipt part-NN.md] [--finish] [--continuity] [--legacy]
```

脚本按 metadata 位置一次性解析布局。检测到根目录与 `_lathe/` 混放辅助文件时停止写入；不得逐文件回退或拼接两套布局。退出码非 0 先修再交付；legacy 课程缺账本时的 `exit 3` 表示下一次写操作先回填。

## 1. 布局与事实源

| 布局 | 判定 | 知识点事实源 | 辅助文件位置 |
|---|---|---|---|
| 新课程 | `_lathe/metadata.json` 存在 | `_lathe/knowledge-points.md` | metadata、knowledge points、research、verify result/workspace 全部在 `_lathe/` |
| 0.6.0 legacy | 根目录 `metadata.json` 存在 | 根目录 `syllabus.json` | 保持根目录旧布局，原地读写，不迁移 |

两处 metadata 同时存在，或已判定布局后另一布局出现任一辅助文件，均为**混合布局**：报告冲突路径并停止写入。正文 `part-*.md` 始终在课程根目录。

## 2. 新课程知识表

### 固定格式

只写一个连续 Markdown 表，表头、顺序和列数固定：

```markdown
# 课程知识点与进度

进度：已完成 1 / 计划内 3（33%）
状态：planned 1 · queued 1 · taught 1 · self-study 0 · dropped_by_user 0 · duplicate 0

| ID | 知识点 | 来源 | 类型 | 状态 | 已讲位置 / 承诺来源 | 备注 |
|---|---|---|---|---|---|---|
| P1-1 | 解释事务提交边界 | plan | main | taught | at:part-01.md#1. 提交一笔事务 | |
| E1-1 | 处理重试幂等性 | exercise | carry | planned | promise:part-01.md | 必做练习 2 |
| U-2 | 区分锁等待与死锁 | user | main | planned | — | 用户原文：锁为什么卡住 |
```

执行以下不变量：

1. **一行一点**；数据行必须连续，每条恰好 7 列。单元格中的 `|` 写成 `\|`，不得含换行。
2. 表头必须逐字使用：`ID`、`知识点`、`来源`、`类型`、`状态`、`已讲位置 / 承诺来源`、`备注`。
3. `ID` 全课程唯一。用户手工新增行可以暂留空 ID；**下一次写操作先分配 ID，再做任何状态修改并运行检查**。只读操作不得擅自补写。
4. `知识点` 非空且不超过 60 字，写成可命名、可解释、可复现的单一产出。
5. **行序 = 默认选点顺序**：越靠前的 `planned` 越先被考虑；用户可通过调整行序表达优先级。**不要写 `计划 Part`，不要给知识点预定归属 Part。**
6. 没有位置时写 `—`，不要留空。缓存行由数据行重建，不得手调数字代替改行。

### 枚举

| 列 | 允许值 | 规则 |
|---|---|---|
| 来源 | `user` / `plan` / `exercise` / `deepen` | 选做练习不入表；部分重叠产生的深化点写 `deepen` |
| 类型 | `main` / `foundation` / `mergeable` / `carry` | 表示写作角色，不表示 Part 归属。`main` / `mergeable` 占构建名额；`foundation` / `carry` 按 writing-core.md 的地基/承接豁免与总章上限执行 |
| 状态 | `planned` / `queued` / `taught` / `self-study` / `dropped_by_user` / `duplicate` | 每行恰有一态 |
| 位置 | `at:<part#标题>` / `promise:<part>` / `dup:<ID或part#标题>` / `—` | 一行最多一种前缀 |

位置格式与状态绑定：

- `taught`：必须写 `at:part-NN.md#<## 标题原文>`；章节须真实存在。带章号标题可按章号命中，文字漂移后仍应刷新。
- `planned` / `queued`：可在 `promise:` 写**作出承诺的 Part**，表示这个点来自那部分的练习；它不表示将来由哪个 Part 兑现，也不预测具体 Part 编号。没有承诺写 `—`。
- `duplicate`：必须写 `dup:<主条目 ID>` 或 `dup:part-NN.md#<标题>`。
- `self-study` / `dropped_by_user`：备注必须写明用户选择、时间或原因；模型不得自行设置。

**到期承诺**：`promise:` 指向的 Part 已经写完，而本条仍是 `planned` / `queued`，即为到期承诺。它在下一次续写中拥有最高选点优先级，并会在收尾时列为剩余知识点；不需要 `计划 Part` 字段来判断。

### 外部清单的结构化备注

从用户已有计划表导入时，`备注` 统一写成一行结构化文本；普通手工条目不强制：

```text
用户原文=<完整原文>；深度=做|讲|知；标记=<原/调/新…>；原编号=<n>；个人掌握=完成|未完成
```

- `深度` 是写作指令，不是状态或类型：`做/讲/知` 的完成标准见 writing-core.md「外部清单深度」。
- `个人掌握` 只供导入报告和人工核对；**绝不据此写 `taught`**，`taught` 仍只由真实 `at:` 证明。
- `原编号` 是外部计划编号，不是 Lathe ID；ID 另按全课程唯一规则分配。
- `深度=` 出现在备注时，`ledger_check.py` 会校验枚举；含 `原编号=` 却缺少深度，或把个人掌握写进状态，均由检查器报错。
- 普通用户清单仍可用自然语言备注，不要为了通过检查伪装成外部导入格式。

### 六态与编辑

按以下流转：

```text
planned → taught | queued
queued → taught
planned | queued → self-study | dropped_by_user   # 仅用户显式决定
self-study → queued                               # 用户重新捡回
新条目 → duplicate                               # 仅语义完全相同
```

用户删除整行属于**主动编辑**，不要按损坏静默重建。仍应先建议保留该行并改成 `dropped_by_user`，以便审计；用户坚持删除时接受删除并在回执说明。无法确认是主动删除还是文件损坏时停止写入，请用户确认。不要建立 ID 镜像来推断删除。

### 进度与缓存

计算：

```text
计划内 = taught + planned + queued
进度 = taught / 计划内
百分比 = 四舍五入到整数；计划内为 0 时写 0%
```

`self-study`、`dropped_by_user`、`duplicate` 不进入分母。状态行固定按六态顺序列出全部计数。进度行和状态行都是**可由表格重建的显示缓存**；数据行冲突时以数据行为准并重写缓存。

## 3. 选点、归一化与配额

### 用户清单来源三选一

一次写操作只选一个用户清单来源，避免重复导入：

1. 用户本次消息直接列出的清单；
2. 用户直接编辑知识表新增的 `来源=user` 行；
3. 用户明确指定的外部清单文件。

同时出现多个来源时先让用户指定一个；不得静默合并。已经存在于知识表的行不是“再次新增”。外部清单只读，不把其路径当第二事实源；归一化后写入知识表。

### 归一化与 ID

- 一条只保留一个可命名产出；“鉴权”这类领域词拆为可解释、可复现的点。
- 用户原编号可用作 ID；冲突时加课程/阶段前缀。无编号时按现有命名序列分配稳定 ID。
- 在备注逐字保留用户原文与拆分关系；不得因改写措辞合并、删减或替换用户意图。
- 标记 `main` / `foundation` / `mergeable`；练习承诺标 `carry`。

### 硬优先级

每次写 Part 时，在**全池**中按以下顺序选点：

1. **已到期的 `promise:` 条目**（承诺来源 Part 已写完）；
2. 本次用户新增条目；
3. `queued`（先进先出）；
4. `planned`（按表内行序）。

**行序是默认推荐，不是死板顺序。** 如果因为用户方向、本地代码进度、前置未满足或深度不合适而跳过行序更靠前的点，必须在写前计划中写明原因，并在回执中列出未选候选。不得静默跳过。

`continuity.next_hook` 只提供衔接语境，不是知识点来源。到期承诺不得被用户新增挤出；确实无法兑现时保持/转为 `queued`，保留原 `promise:`，在正文和回执点名，不预测具体 Part。

### 配额应用

按 writing-core.md 的现有知识点配额决定容量：`main` / `mergeable` 使用最多 7 个构建名额；用户新增、到期承诺、`queued` 与 `planned` 只要属于这两类就进入同一名额池；`mergeable` 可同章讲两个点，但仍分别计数。正常目标是 4–7；**候选确实不足 4 时不凑数**。`foundation` 使用地基章节额度，`carry` 使用 §0 承接额度；两者不占构建名额，但都计入“地基 + 承接 + 构建 ≤9”的总章上限。

容量不足时按硬优先级保留，其他点留在池中：本部分用户新增或到期承诺确实装不下时改为 `queued`；后续候选保持 `planned`。不要把点塞入 `next_hook`，也不要给 `course_plan` 追加点级“补：”项。

### 去重

| 判断 | 处理 |
|---|---|
| 与 `taught` / `planned` / `queued` 语义完全相同 | 后来者记 `duplicate`，用 `dup:` 指向主条目 |
| 仅部分重叠 | 改写为“深化：<差异>”，来源写 `deepen`，照常占配额或排队 |
| 拿不准 | 保留为不同条目 |

主条目优先级：`user` > `exercise` > `plan` > `deepen`。去重必须出现在写前确认与覆盖回执，不得靠删除行去重。

### queued 闸门

默认上限 14 条。入队后 11–14 条时提示积压；会超过 14 条时停止写入并给三选一：

1. **拆 Part（默认）**：改写 `course_plan` 叙事大纲，把下一段拆成更小的交付单元；
2. **降级**：仅经用户明确选择，把溢出行改为 `self-study` 并在备注记原因；
3. **缩减**：仅经用户明确选择，把指定行改为 `dropped_by_user`。

所有状态只写在知识表；不要在 research 建自学或已讲镜像。连续两次净增至少 3 条或闸门触发时，先给拆分草案，用户确认后再改 `course_plan` 与相关状态。

## 4. 写前确认、正文留痕与回执

### 写前计划确认

以下任一成立时，先发计划并等待回复：生成；用户给清单；存在顺延/去重/闸门/重规划；池中 planned 需要增删改；legacy 首次回填；0.6.1 八列表迁移。用户明确“直接写/不用确认”可跳过常规确认，但生成时的课程大纲确认与 0.6.1 迁移确认不得跳过。

计划至少列出：

```text
写前计划确认（part-NN）
① 清单归一化与 ID：…
② 本次选点依据：用户需求 … ｜ 上次结束状态 … ｜ 本地代码进度 … ｜ 到期承诺 …
③ 本部分讲：<ID 列表>（构建 N / 通常 4–7、最多 7；地基 F；承接 C；总章 T / ≤9）
④ 未选候选与原因：<池中行序前几条；为什么这次不讲>
⑤ 顺延、去重、闸门与 course_plan 大纲调整：…（仅触发时）
```

用户改计划后直接按新计划执行。用户新增行先分配 ID；用户删除条目时建议改 `dropped_by_user`，并尊重其明确选择。

### 正文留痕

- `本部分不覆盖`：按 ID 点名本次未选且仍留在池中的条目，写“后续优先”，**不预测具体 Part 编号**。
- 讲到旧 `queued` 或到期承诺时：在章节开头回指来源。
- 档 3 练习题面后：写“本题涉及的知识点（X，池中 ID `K`）不在本部分展开，后续优先讲”。
- 实际讲到的 Part 与最初预想不同时，只更新知识表与新正文，不回改旧 part。

### 交付回执

交付开头报告：本部分覆盖、未选候选（至少列出行序最靠前的几条及原因）、顺延、去重、计划章数/实写章数、试跑、六态统计与当前 queued。写前计划中的每一点必须落入覆盖、未选、顺延、去重或用户处置之一。

有 shell 时直接粘贴脚本输出：

```text
python3 <SKILL_DIR>/scripts/part_lint.py <课程根目录>/part-NN.md
python3 <SKILL_DIR>/scripts/trial_run.py <课程根目录>/part-NN.md --run
python3 <SKILL_DIR>/scripts/ledger_check.py <课程根目录> --receipt part-NN.md
```

## 5. 练习承接与承诺门禁

必做题最多 2 道引入本部分未讲的新概念；选做题可引入新概念，但只给线索与官方文档入口，不入表。必做题的新概念逐条入表，`来源=exercise`、`类型=carry`，并选择：

| 档 | 处理 |
|---|---|
| 1 融入 | 与池中某个构建点直接重合；写 `planned` + `promise:<作出承诺的 part>`，下次选点时按硬优先级讲透 |
| 2 承接章 | 下一 Part 单独在 §0 讲；同样写承诺 |
| 3 顺延 | 写 `queued` + `promise:<作出承诺的 part>`，正文按 ID 提醒 |

档 1 跟随它并入的构建知识点占位；档 2 使用 §0 承接额度；档 3 本次不讲、进入 queued。档 1 必须包含“原疑问、解释、可运行验证”；缺一按档 2 处理。承接章放在前置条件之后、第一个构建章之前，不写练习。

承诺到期时执行最高优先级：讲掉后改 `taught` 与 `at:`；没讲成则改/保持 `queued`、保留原 `promise:`，并在回执单列“未兑现”。不得把未兑现承诺悄悄留成普通 `planned`，也不得自行降级或删除。**知识表本身就是练习承接记录，不维护 continuity 镜像。**

## 6. Legacy `syllabus.json` 原地兼容

对根目录 `metadata.json` 判定出的旧课程：

1. 继续读取和写回根目录 `syllabus.json`；保持旧 JSON point 字段、未知字段和“一行一点”格式。
2. 继续接受旧字段 `id`、`text`、`original`、`parent`、`src`、`from`、`tag`、`plan_ref`、`status`、`at`、`depth`、`dup_of`、`note`、`promised_by`；状态语义与优先级按本文执行。
3. **`plan_ref` 只是 legacy 兼容字段**：选点、收尾和门禁都不再读它；不要按它把点绑定到 Part，也不要因为它缺失而拒绝写入。保留原值即可。
4. 账本不存在时，下一次写操作从正文、旧 metadata 和路线图推断回填，先展示结果再写；无法恢复的删除/去重历史明确报告。
5. 只在旧位置原地维护旧课已有 `metadata.json`、`syllabus.json`、`research.md`、`verify-result.json`、`.lathe-verify/`；**不创建 `_lathe/`，不迁移，不把新旧文件逐个互相回退。**
6. 旧 metadata 的点级镜像字段仅作读取兼容线索；原地写回可保留未知字段，但不得再更新、依赖或复制为新事实源。

## 7. 收尾：允许未学完，但必须留提示

`completed` 不再要求所有点都是 `taught`。用户可以通过知识表自行判断是否学完；如果仍有 `planned` / `queued`，允许收尾，但**总结 Part 必须写提示**：

```markdown
> [!WARNING]
> **完成状态：未学完（剩余 N 条知识点）。**
> 未讲清单见下方「未讲清单（按 ID）」。之后可以运行 `/lathe 续写 <slug>` 继续学习剩余知识点；续写会把课程重新开放为 `unverified`。
```

执行规则：

1. 收尾前运行 `python3 <SKILL_DIR>/scripts/ledger_check.py <COURSE_DIR> --finish`，拿到全部剩余 ID。
2. 总结的 `## 未讲清单（按 ID）` 必须逐条列出剩余 `planned` / `queued`，并写清“为什么没讲 / 怎么继续”。
3. 总结写入后运行 `python3 <SKILL_DIR>/scripts/ledger_check.py <COURSE_DIR> --finish --receipt <总结文件>`。脚本会校验“未学完”、全部剩余 ID 与“续写”提示；缺任何一项先补再交付。
4. 没有剩余点时，正常写“全部学完/全部已处置”，不需要未学完提示。
5. `status` 仍可设为 `completed`；后续 `/lathe 续写` 会把它重新开放为 `unverified`，剩余点继续参与选点。

**不要**把剩余点悄悄标成 `self-study` / `dropped_by_user` 来绕过提示；这两个状态只能由用户明确选择。

## 8. 写回检查

写回前逐项确认：

1. 布局唯一，命令传课程根目录；新课程所有辅助文件都在 `_lathe/`。
2. 固定七列、一行一点、`\|` 已转义；空 ID 已在写操作开始时分配。
3. 枚举、六态、`at:` / `promise:` / `dup:` 合法；缓存按真实行重建。
4. 到期承诺先于用户新增，其后才是 queued 与 planned（按行序）；构建、地基与承接分别使用 writing-core.md 的对应额度。
5. 写前计划每一点在正文、知识表与回执闭合；未选候选与原因已写进回执；用户主动删除未被误判为普通损坏。
6. queued 未越过闸门；模型没有自行设置 `self-study` / `dropped_by_user`。
7. 外部导入备注的 `深度=做/讲/知` 已按 writing-core.md 执行；`个人掌握` 没有进入 `status`。
8. 运行 `ledger_check.py <课程根目录>`；收尾再加 `--finish`（有总结文件时带 `--receipt`），continuity 预算检查用 `--continuity`。

## 9. 0.6.1 八列表迁移

0.7.0 只读兼容 0.6.1 的八列知识表（多一个 `计划 Part`）。遇到八列表时：

1. 先运行 `ledger_check.py <COURSE_DIR>`；检查器会列出每条旧 `计划 Part` 的迁移对照。
2. 向用户展示“删除 `计划 Part` 列，点不再归属 Part，行序成为默认顺序”的对照，得到明确确认后才写入。
3. 写入时按 0.7.0 七列渲染；旧 `plan_ref` 值丢弃，不写进正文、metadata 或 research。
4. 不要静默迁移，也不要在未确认时顺手改用户的知识表。
5. 0.6.0 legacy `syllabus.json` 不在迁移范围内，继续原地兼容。
